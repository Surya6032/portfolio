context

Lead teams (3–5 engineers) at Cencora, a Fortune 10 pharmaceutical distributor. Platform needed to unify clinical, financial, and pharmacy datasets at 5–10 TB/day from multiple upstream source systems across all business units.

problem

Data siloed across domains. No enforced schema contracts between source systems and consumers. Analytics teams maintained conflicting transformation logic. Upstream schema changes propagated unchecked — corrupting reports silently. Full-table reprocessing on every run regardless of delta.

architecture

fig.1 — medallion_lakehouse.arch · proprietary business logic omitted

approach
  1. Defined layer contracts: Bronze = append-only raw; Silver = cleansed/conformed; Gold = aggregated/business-ready
  2. Configured schema enforcement at Bronze to reject malformed records at source — eliminated silent corruption reaching reports
  3. Implemented CDF for incremental Bronze→Silver→Gold — no full table scans on 5–10 TB/day datasets
  4. Applied Z-Order clustering on Gold tables optimized for primary query patterns (financial date ranges, clinical patient IDs)
  5. Standardized all ingestion via ADF with consistent naming, retry logic, and monitoring across all four domains
  6. Wrote internal ETL coding standards and code review gates adopted as team standards
results
  • Single org-wide source of truth across clinical, financial, and pharmacy data — adopted by all analytics and reporting consumers
  • Schema enforcement eliminated the recurring class of silent data corruption bugs at Bronze ingestion
  • CDF incrementality enabled the 24h→15min latency reduction on financial reporting (see project 002)
  • Multi-million dollar platform initiative delivered on time within team headcount
learning
// retrospective

Would introduce formal upstream data contracts earlier. Schema enforcement catches failures at ingest; formalizing expectations with source system owners catches them before the pipeline — far cheaper on a 5–10 TB/day system.

context

Financial reporting pipeline at Cencora serving FP&A and executive leadership. Ran once nightly as a full batch job, completing ~6am. Finance teams arrived at 8am making decisions on data at least 26 hours old.

problem

The 24-hour lag had real cost — pricing decisions and exception handling delayed by a full day. Root issue: full-table read/write on every run even when only 2–3% of records had changed overnight.

approach
  1. Profiled existing pipeline — full-table read was the bottleneck, not cluster size
  2. Switched to Delta Lake CDF — process only new/modified records since last successful run
  3. Replaced scheduled nightly trigger with event-driven Databricks Jobs — fires on upstream data landing in ADLS
  4. Built SLA monitoring and retry logic — new pipeline needed higher reliability than once-a-night batch
  5. Ran 3 weeks parallel execution with automated output comparison before decommissioning old pipeline
results
  • 98% latency reduction: 24 hours → 15 minutes from source data landing to Gold-layer availability
  • Finance and executive teams had same-day data for the first time
  • Zero data correctness issues post-cutover; 3-week parallel run confirmed full output parity
  • Monitoring layer reduced on-call incidents for the data engineering team
learning
// retrospective

Three weeks of parallel validation felt conservative — it was right. Financial data discrepancies in regulated environments carry significant remediation cost. Now treat parallel validation as non-negotiable for financial or compliance-sensitive pipelines.

context

Production PySpark pipelines handling 5–10 TB/day of mixed structured (SQL Server, Azure SQL) and semi-structured (JSON, nested pharmacy records) data. Three jobs running 40–60% slower than original benchmarks. Downstream SLAs being missed. Compute costs growing faster than data volume — a diagnostic signal.

problem

The instinct was to increase cluster size. That was the wrong answer. Jobs ran, produced correct output — they were just slow. Inefficiency was in code and configuration, not infrastructure.

approach
  1. Profiled first using Spark UI DAG visualization and query execution plans — identified wide shuffles, full table scans, skewed partitions
  2. Rewrote partition scheme using high-cardinality date/entity columns — enabled partition pruning on filtered reads
  3. Added broadcast join hints where one side qualified — eliminated expensive sort-merge shuffle stages
  4. Added intermediate caching at correct DAG checkpoints to avoid redundant I/O
  5. Tuned shuffle partition counts, executor memory, and parallelism per job profile
  6. Documented tuning playbook — now mandatory pre-production checklist for all new pipeline builds
results
  • 30% average throughput improvement across three optimized pipelines
  • All downstream SLA windows met consistently even as data volume continued growing
  • DBU consumption reduced — compute tracked volume growth rather than outpacing it
  • Tuning playbook adopted as mandatory pre-production checklist across the team
learning
// retrospective

Profile before you optimize — always. On 5–10 TB/day workloads adding compute is expensive and usually wrong. Every bottleneck was in the code. I now treat profiling as the first deliverable on any performance investigation.

context

Data pipelines at Cencora were deployed manually — engineers pushed changes directly to Databricks workspaces with no version control gates, automated testing, or rollback path. In a regulated environment handling clinical and financial data, this was both a reliability and compliance risk.

problem

Three overlapping failure modes: deployment risk (anyone could push to prod), quality gaps (data issues reached Gold before detection), and audit exposure (no traceable record of changes in a HIPAA-adjacent environment).

approach
  1. GitHub Actions: automated test runs on every PR — unit tests for transform logic, schema validation, integration tests against staging
  2. Azure DevOps: release pipelines with required approvals — every production change has audit-logged paper trail
  3. ARM Templates: infrastructure-as-code for Azure resource provisioning — infra changes reviewed same as code
  4. Great Expectations: checkpoints between Bronze→Silver and Silver→Gold covering schema, nulls, referential integrity, value ranges
  5. Two live working sessions with team — walkthrough from local dev through CI to release — plus internal runbook
results
  • Zero manual deployments to production — every change goes through automated CI/CD
  • Pre-production quality gates catch schema drift, null violations, and integrity failures before business-facing tables
  • Audit-ready deployment history — traceable by engineer, timestamp, and approver
  • Framework adopted as team standard — all new pipelines built against same CI/CD and quality gate patterns
learning
// retrospective

Process changes are adoption problems, not technical ones. The two live working sessions mattered more than the docs. Start team process changes with walkthroughs much earlier in the rollout.

I'm a Senior Data Engineer based in Dallas, TX. For the last five years I've been building the infrastructure that sits between raw data and the decisions organizations make with it — pipelines, lakehouses, and the quality systems that keep them honest.

Most of my work has been in healthcare and pharmaceutical distribution, where data reliability isn't negotiable. Clinical datasets, financial records, pharmacy operations data — these need to be right, traceable, and on time. That constraint has made me a more disciplined engineer than most environments would have.

I care about the details that make systems maintainable: schema contracts, incremental load patterns, profiling before optimizing, and documentation that junior engineers can actually use. I've led teams of 3–5 engineers and believe good architecture is only as good as the standards the team executes consistently.

// principles
profile_before_optimize()

Spark bottlenecks are almost never where intuition says. I start every investigation with the query plan and DAG, not assumptions. On 5–10 TB/day workloads, a bad partition strategy costs real money.

reliability_over_features()

A pipeline that runs once and breaks is worth less than a boring pipeline that runs every day without incident. I bias toward proven patterns — incremental loads, schema enforcement, idempotent writes.

standards_compound()

Good naming conventions and shared ETL patterns feel like overhead on day one. On day 300, they're why a junior engineer can debug a production issue without escalating.
