context

Part of the data engineering team (3–5 engineers) at a Fortune 10 pharmaceutical distributor. Led the build of a unified data platform to centralize clinical, financial, and pharmacy datasets — processing 5–10 TB/day from multiple upstream source systems.

problem

Data siloed across domains with no enforced schema contracts. Analytics teams maintained conflicting transformation logic. Upstream schema changes corrupted reports silently. Every pipeline run reprocessed the full dataset regardless of delta — expensive at 5–10 TB/day.

architecture

fig.1 — medallion_lakehouse.arch · proprietary business logic omitted

approach
  1. Defined layer contracts: Bronze = append-only raw; Silver = cleansed/conformed; Gold = aggregated/business-ready
  2. Configured schema enforcement at Bronze — malformed records rejected at source, silent corruption eliminated
  3. Implemented CDF for incremental Bronze→Silver→Gold — no full table scans on 5–10 TB/day datasets
  4. Applied Z-Order clustering on Gold tables optimized for financial date ranges and clinical patient ID queries
  5. Standardized all ingestion via ADF with consistent naming, retry logic, and monitoring across four domains
  6. Established team coding standards and code review gates, adopted as team-wide practices
results
  • Single org-wide source of truth across clinical, financial, and pharmacy — adopted by all analytics and reporting consumers
  • Schema enforcement eliminated recurring silent data corruption bugs at Bronze ingestion
  • CDF incrementality enabled the 24h→15min financial reporting latency reduction (see project 002)
  • Multi-million dollar platform initiative delivered on time within existing team headcount
learning
// retrospective

Would introduce formal upstream data contracts earlier. Schema enforcement catches failures at ingest — formalizing expectations with source system owners catches them before the pipeline, far cheaper at 5–10 TB/day.

financial_pipeline.latency ›

context

Financial reporting pipeline serving FP&A and executive leadership. Ran once nightly, completing around 6am. Finance teams arrived at 8am making decisions on data at least 26 hours old. Leadership flagged the lag as a strategic blocker.

problem

Full-table read/write on every run — even when only 2–3% of records had changed overnight. The 24-hour lag delayed pricing decisions, contract adjustments, and exception handling by a full business day.

approach
  1. Profiled the existing pipeline — full-table read was the bottleneck, not cluster size
  2. Switched to Delta Lake CDF to process only new/modified records since last successful run
  3. Replaced scheduled nightly trigger with event-driven Databricks Jobs firing on upstream data landing in ADLS
  4. Built SLA monitoring and retry logic for the new always-on pattern
  5. Ran 3 weeks of parallel execution with automated output comparison before decommissioning the old pipeline
results
  • 98% latency reduction: 24 hours → 15 minutes from source data landing to Gold-layer availability
  • Finance and executive teams had same-day data for the first time
  • Zero correctness issues post-cutover — 3-week parallel run confirmed full output parity
  • Monitoring layer reduced on-call incidents for the data engineering team
learning
// retrospective

Three weeks of parallel validation felt conservative — it was the right call. Financial data discrepancies in regulated environments carry significant remediation cost. Parallel validation is now non-negotiable for any financial or compliance-sensitive pipeline migration.

Profiling-first investigation across three production PySpark jobs on 5–10 TB/day workloads. Partitioning, broadcast joins, caching, and executor tuning to recover 30% throughput.

context

Production PySpark pipelines handling 5–10 TB/day of mixed structured and semi-structured data. Three jobs running 40–60% slower than original benchmarks, missing downstream SLAs. Compute costs growing faster than data volume — a clear diagnostic signal.

problem

The instinct was to add compute. That was the wrong answer. Jobs ran and produced correct output — they were just slow. The inefficiency was in code and configuration, not the cluster.

approach
  1. Profiled using Spark UI DAG visualization and query execution plans — identified wide shuffles, full table scans, and skewed partitions
  2. Rewrote partition scheme with high-cardinality date/entity columns — enabled partition pruning on filtered reads
  3. Added broadcast join hints where one side qualified — eliminated expensive sort-merge shuffle stages
  4. Added intermediate caching at correct DAG checkpoints to avoid redundant I/O
  5. Tuned shuffle partition counts, executor memory, and parallelism per job profile
  6. Documented a tuning playbook — now mandatory pre-production checklist for all new builds
results
  • 30% average throughput improvement across the three optimized pipelines
  • All downstream SLAs consistently met even as data volume continued growing
  • DBU consumption reduced — compute tracked data volume growth rather than outpacing it
  • Tuning playbook adopted as mandatory pre-production checklist across the team
learning
// retrospective

Profile before you optimize — always. On 5–10 TB/day workloads, adding compute is expensive and usually wrong. Every bottleneck here was in the code. Profiling is now always the first deliverable on any performance investigation.

context

Pipelines were deployed manually — engineers pushed directly to Databricks workspaces with no version control gates, automated testing, or rollback path. In a regulated environment handling clinical and financial data, this was both a reliability and compliance risk.

problem

Three overlapping failure modes: deployment risk (anyone could push to prod), quality gaps (data issues reached Gold before detection), and audit exposure (no traceable record of changes in a HIPAA-adjacent environment).

approach
  1. GitHub Actions: automated test runs on every PR — unit tests, schema validation, integration tests against staging
  2. Azure DevOps: release pipelines with required approvals and audit-logged trail for every production change
  3. ARM Templates: infrastructure-as-code for Azure provisioning — infra changes reviewed same as code changes
  4. Great Expectations: checkpoints between Bronze→Silver and Silver→Gold covering schema, nulls, referential integrity
  5. Ran two live working sessions with the team — walkthrough from local dev through CI to release, plus internal runbook
results
  • Zero manual deployments to production — every change goes through automated CI/CD
  • Pre-production quality gates catch schema drift and integrity failures before business-facing tables
  • Audit-ready deployment history — traceable by engineer, timestamp, and approver
  • Framework adopted as team standard — all new pipelines built against same CI/CD and quality gate patterns
learning
// retrospective

Process changes are adoption problems, not technical ones. The two live working sessions mattered more than the documentation. Start team process changes with walkthroughs much earlier in the rollout.

03 about.md

I'm a Senior Data Engineer based in Dallas, TX. For the last five years I've been building the infrastructure that sits between raw data and the decisions organizations make with it — pipelines, lakehouses, and the quality systems that keep them honest.

Most of my work has been in healthcare and pharmaceutical distribution, where data reliability isn't negotiable. Clinical datasets, financial records, pharmacy operations — these need to be right, traceable, and on time. That constraint has made me a more disciplined engineer than most environments would produce.

I care about the details that make systems maintainable: schema contracts, incremental load patterns, profiling before optimizing, and documentation junior engineers can actually use. I've led teams of 3–5 engineers and believe good architecture is only as good as the standards the team executes consistently.

// engineering principles
profile_before_optimize()

Spark bottlenecks are rarely where intuition says. I start every investigation with the query plan and DAG. On 5–10 TB/day workloads, a bad partition strategy has real dollar cost.

reliability_over_features()

A pipeline that runs once and breaks is worth less than a boring pipeline that runs every day without incident. Incremental loads, schema enforcement, idempotent writes — the patterns that hold up.

standards_compound()

Shared naming conventions and ETL patterns feel like overhead on day one. On day 300, they're why a junior engineer can debug a production incident without escalating.
